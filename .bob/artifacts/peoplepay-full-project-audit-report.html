4. 🔴 Critical Issues

C1 — Duplicate Route Registration for /api/payruns
server/src/app.js — lines 84 & 88

payrunRoutes is registered twice on the same path /api/payruns. Express processes the first match and the second binding shadows it for certain middleware behaviors, creating unexpected behavior for POST/GET chains and wasting a handler slot.

Fix: Remove the duplicate app.use('/api/payruns', payrunRoutes); on line 88.

C2 — Missing Critical .env Keys in .env.example
server/.env.example

The .env.example only lists database config. The following required environment variables are used in code but not documented in the example file, so any new developer will get runtime crashes:

  • JWT_SECRET — used in auth.middleware, token.utils (hard crash on startup)
  • JWT_REFRESH_SECRET — used in token.utils for refresh tokens
  • JWT_EXPIRE / JWT_REFRESH_EXPIRE
  • REDIS_URL / REDIS_HOST / REDIS_PORT / REDIS_PASSWORD — Redis required for auth
  • CLIENT_URL — CORS origin (defaults to localhost:5173 but undocumented)
  • OTP_SECRET — HMAC key for OTP hashing
  • SMTP keys for Nodemailer (EMAIL_HOST, EMAIL_PORT, EMAIL_USER, EMAIL_PASS, etc.)
C3 — Client VITE_API_BASE_URL Points to Wrong Port
client/.env.example — line 1

VITE_API_BASE_URL=http://localhost:3000/api — but the server runs on port 5000 (per server/.env.example PORT=5000). If no .env is created, apiClient.js defaults to port 3000, and every API call fails with ECONNREFUSED.

Fix: Change .env.example to http://localhost:5000/api.

C4 — Hardcoded Admin Credentials & Personal Email in seed.js
server/seed.js — lines 21, 29, 44

The seed file contains a personal email address (sanjibbayen11@gmail.com) and hardcoded password Admin@123 committed to the repository. These will persist in git history. Any clone of the repo knows the initial admin credentials.

Fix: Move seed credentials to environment variables (SEED_ADMIN_EMAIL, SEED_ADMIN_PASSWORD).

C5 — Auth Middleware Uses JWT_SECRET but Refresh Flow Uses Separate JWT_REFRESH_SECRET
server/src/middleware/auth.middleware.js — line 32 vs server/src/utils/token.utils.js — line 62

The protect middleware verifies tokens with JWT_SECRET, but the refresh token is signed with JWT_REFRESH_SECRET. If JWT_REFRESH_SECRET is undefined (not set), refresh tokens are signed with undefined as secret — which Node's jsonwebtoken library accepts silently, making all refresh tokens share the same trivially-guessable secret. This is a security vulnerability.

Fix: Validate that both secrets are non-empty strings on server startup; throw an error if either is missing.

C6 — Token Stored in Both localStorage & sessionStorage Simultaneously
client/src/redux/slices/authSlice.js — lines 109–126

On every setCredentials, the JWT access token is written to 4 keys across both localStorage and sessionStorage. This defeats the security benefit of using sessionStorage (tab-scoped). Any XSS attack gets the token from the persistent localStorage. The mirroring also means logout must clear all 4 keys reliably (currently done, but fragile).

Fix: Pick one storage strategy: use sessionStorage only for better security, or localStorage only for UX — not both simultaneously.

5. 🟡 Warnings

W1 — No Rate Limiting on Login Endpoint
server/src/routes/auth.routes.js — line 25

The POST /auth/login route is entirely public with no rate limiting applied. The custom rateLimit middleware exists in auth.middleware.js but is not used on the login route. Brute-force attacks on passwords are unrestricted.

W2 — Payrun Routes Missing Role-Based Authorization
server/src/routes/payrun.routes.js — comment line 18

The file has a comment saying "NO PERMISSION CHECKS". All payrun routes only use protect (authentication) but not restrictTo or requirePermission. Any authenticated user, including a basic employee, can create, compute, or mark payruns as paid.

W3 — Redis Key Prefix Collision Risk
server/src/config/redis.config.js — line 61

Redis keys use a global prefix peoplepay360:, but token blacklist lookups in auth.middleware.js use redis.get('blacklist:${token}') — without the prefix. Because ioredis automatically prepends the keyPrefix to all commands, the actual Redis key becomes peoplepay360:blacklist:{token}. The blacklistToken utility in token.utils.js also uses the same client, so this is actually consistent — but only because both use the same client. If any code ever constructs a raw Redis key manually without going through the ioredis client, the prefix will be missing and tokens will never be found as blacklisted.

W4 — OTP Cooldown Key Path Inconsistency
server/src/utils/otp.utils.js — lines 86 vs 185

createOTP stores cooldown at key otp:{purpose}:{email}:cooldown (line 86), but checkOTPRateLimit checks for cooldown at otp:{purpose}:{email.toLowerCase()}:cooldown (line 185). These are two different lookups: the cooldown stored by createOTP is never found by checkOTPRateLimit, breaking the 1-minute re-send cooldown.

W5 — ScheduleDaysEditor Page Missing from App Routes
client/src/pages/schedules/ScheduleDaysEditor.jsx vs client/src/routes/AppRoutes.jsx

The ScheduleDaysEditor page component exists but has no corresponding route defined in AppRoutes.jsx. It is unreachable from the UI.

W6 — SalaryRuleList.jsx is an Orphan Page
client/src/pages/salary/SalaryRuleList.jsx

This component exists alongside SalaryRulesPage.jsx but is not imported or used anywhere. Either it duplicates SalaryRulesPage or it is dead code.

W7 — Express 5 in Production Use (Still RC-era Breaking Changes)
server/package.json — "express": "^5.2.1"

Express 5 changed error handling for async routes — rejected promises are now automatically forwarded to error middleware (good), but there are breaking changes to req.query parsing and router behavior. Some patterns in the controllers may silently behave differently than intended vs Express 4.

W8 — initializeDatabase Only Runs sync in Development
server/src/models/index.js — lines 76–78

Database schema sync (sequelize.sync({ alter: false })) is gated behind NODE_ENV === 'development'. In production, no schema migration runs. If the database schema is out of sync (e.g. new models were added), production will throw SQL errors at runtime with no migration path.

Recommendation: Use a migration tool (Sequelize CLI migrations or Umzug) instead of sync.

6. 🔵 Minor / Info

I1 — Tailwind v4 + PostCSS Dual Configuration
client/package.json, client/postcss.config.js, client/vite.config.js

Both @tailwindcss/vite (Vite plugin) and @tailwindcss/postcss (PostCSS plugin) are installed. Tailwind v4 recommends using only the Vite plugin when using Vite — running both can cause double-processing. tailwind.config.js is also present, which is the v3 config format and may conflict with v4's CSS-first config.

I2 — deleteCacheByPattern Has a Commented-Out Alternative Still in File
server/src/utils/cache.utils.js — lines 38–49

The old redis.keys() implementation is left as a comment directly above the new SCAN-based implementation. Clean up the dead code.

I3 — activeNav Prop Passed to AppShell But Not Used in AppLayout
client/src/routes/AppRoutes.jsx vs client/src/layouts/AppLayout.jsx

Every route in AppRoutes.jsx passes an activeNav prop to AppShell, which passes it to AppLayout — but AppLayout does not use or forward the activeNav prop. The sidebar active-state highlighting will not work through this prop chain unless SidebarDrawer reads it from another source.

I4 — No Test Suite Configured on Either Side
server/package.json — scripts.test; client/package.json — no test script

The server's test script is the placeholder "echo Error: no test specified && exit 1". The client has no test script at all. No Jest, Vitest, or Supertest configuration exists in the project.

I5 — seed.js Does Not Call initializeDatabase() / sync()
server/seed.js

The seed script calls sequelize.authenticate() and imports models (which auto-initializes them), but never calls sequelize.sync(). If the database tables do not yet exist, the seed will fail with a table-not-found error. The seed should ensure tables exist before inserting data.

7. ✅ What Is Working Well

Solid Authorization Architecture

JWT + OTP 2FA + Magic Link onboarding + Redis blacklist + refresh token rotation is a well-thought-out security model.

Clean Separation of Concerns

Controllers, models, routes, middleware, utils, and services are cleanly separated. Model associate() patterns are correct for Sequelize.

Good Error Handling Strategy

The global errorHandler middleware correctly categorizes Sequelize, JWT, PostgreSQL, and Redis errors into typed AppError responses. asyncHandler wraps all controllers.

Real-Time Notifications via Socket.IO

socket.service.js implements user-specific rooms (user:{id}) and role rooms (role:{name}), allowing targeted real-time events including unread count push.

Token Refresh & Retry Queue on Client

apiClient.js implements a proper retry queue that holds concurrent 401 requests until a single token refresh completes, avoiding thundering-herd token refresh storms.

Progressive Tax Calculation Engine

The payrun controller includes a real multi-slab tax engine with surcharge and cess calculations, indicating serious payroll domain modeling.
